### SUGGESTION (nice to fix)

- S1. The new `reused: bool` field on `ClusterResponse` is an additive
  API change that helps callers tell reuse from a fresh task. It is not
  documented in any spec or storage contract. **Recommendation**: add
  one sentence to the `server-directory-scan` spec or to a new
  `docs/01-architecture/api-contract.md` describing the field, or
  mention it briefly in the design doc's API data-flow section.
- S2. `ClusterAnalyzer._record_terminal_failure` does not need `self`
  (it only reads `self._data_dir` indirectly through the bound method
  call, and even that could be eliminated). **Recommendation**: convert
  to a `@staticmethod` taking `(data_dir, task_output, reason)` so the
  background task can call it without instantiating a second analyzer.
  This is purely a code-cleanliness improvement.
- S3. The in-memory `ClusterTaskRegistry` is reset on server restart,
  so a long-running cluster task's `task_id` cannot be looked up
  through admission control after a restart. The design explicitly
  defers persistence to Phase 2. **Recommendation**: leave as-is for
  Phase 1; mention the restart behavior in the design doc or in the
  `large-log-cluster-scaling-design.md` "Migration Plan" section.
- S4. The process-stats collector in `collect_process_stats.ps1` uses a
  `Start-Sleep -Seconds ([Math]::Max(1, $SampleIntervalSeconds))` after
  the stop-file is created. This is a heuristic; a slow collector tick
  could lose its last sample. **Recommendation**: in `run_analysis_bench.ps1`,
  send the stop signal and then `Wait-Process` on the collector handle
  (with a timeout) before tearing down, so the last sample is always
  flushed.
